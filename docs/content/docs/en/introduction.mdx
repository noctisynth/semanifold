Semifold separates **release decisions** from **release side effects**. It calculates what should happen first, presents that calculation as a plan, and only applies file or network changes through an explicit command.

This matters in a mixed workspace: Cargo, npm, Python packaging, and C++ projects do not share manifest formats or publishing commands, but they still need one answer to “what releases, in which order, and why?”

## The five objects in the workflow

### PackageId

A PackageId is the stable key used in `.changes/config.toml` and changesets. An ecosystem adapter discovers a package's manifest name, version, dependencies, and candidate edits, but Semifold does not silently replace your configured identity with a registry name.

### Ecosystem adapter

An adapter owns ecosystem-specific discovery, inspection, and edit planning. Built-in adapters cover Rust, Node.js, Python, and C++. Publishing credentials, Forge operations, and release orchestration stay outside the adapter boundary.

### Changeset

A changeset is a small Markdown file under `.changes/`. Its front matter maps PackageIds to bump levels and optional changelog tags; its body explains the user-visible change.

```md
---
my-package: "minor:feat"
---

Add the public API.
```

`feat` chooses a changelog section. It does not mean “publish to the feature channel.” Stable and named channels are package release state configured separately.

### Release plan

`smif status` combines changesets, current package versions, dependency constraints, configured relationships, and release-channel state into an immutable plan. Each planned bump carries a reason, so reviewers can distinguish a direct changeset from a dependency-propagated release.

`smif version` uses the same planning path. If the workspace inputs change after you inspect status, run status again instead of assuming the old plan is still valid.

### Publish plan

Publishing begins from the versions and changelogs present after versioning. The plan validates pre-checks and commands, orders packages by the workspace graph, and keeps registry and Forge outcomes separate. A partial failure therefore has explicit succeeded, failed, and not-started facts instead of a single ambiguous error.

## What Semifold changes

During versioning, Semifold may update package versions, internal dependency requirements, changelogs, lockfiles through configured post-version commands, and pending changesets. Every file edit is planned and validated before it is written.

During publishing, Semifold may run configured registry commands and, when requested in CI, create GitHub Releases and upload declared assets. `--dry-run` skips mutating release effects, but still permits read-only registry preflight and commands explicitly configured with `dry-run = true`.
